ADA-PARC. Repository Architecture Map

Website Design Repository

A guide to ADA-PARC-Website-Design. What renders the site, how the pages fit together, and where the data comes from. Prepared 20 July 2026.

This repository is the public website. It is an R and Quarto project that renders an interactive Shiny dashboard of disability outcomes for the United States. One document, ADA_PARC.Rmd, is the whole application. It reads finished datasets produced by the data pipeline repo, then presents them as maps, tables, scorecards, and factsheets, and deploys to shinyapps.io.

The mental model to hold onto is a storefront rather than a factory. The hard work of gathering and shaping data happens in a separate repository, the data pipeline. This repository receives the finished datasets and is concerned only with presentation. That means the questions a maintainer answers here are about how information looks and behaves for a member of the public. How does a map read at a glance, how does a table stay legible on a phone, how does a keyboard user move between tabs, how does the brand feel consistent from page to page. Understanding that division of labor prevents a common mistake, which is trying to fix a data problem by editing the website. If a number is wrong, the fix almost always belongs upstream in the pipeline.

This document is written to be handed to whoever leads the website next. It explains not only where files live but why the site is built as a single flexdashboard document, so a new maintainer can extend it confidently.

The render flow at a glance

Prepared data enters from the pipeline. The flexdashboard app renders it live in a Shiny runtime. Scorecards and factsheets render from their own Quarto documents. The whole thing deploys to shinyapps.io. The word render is worth pausing on, because it explains a lot about how the site behaves. Much of the page is not a static file sitting on a server. It is produced on demand when a visitor interacts with a control, which is what makes the maps and tables respond to a dropdown selection. That interactivity is powerful, but it also means the running app depends on a live R session on shinyapps.io, and that some outputs such as the scorecards are generated at run time rather than served from a saved copy.

Data in App Render Deploy
Where the data comes from. The five datasets in data/final/ (national_data.Rds, tracts_data.Rds, tracts_sf.Rds, city_place_full.Rds, dict_location_crosswalk.Rds) are not built here. They are produced by the ADAPARCDataPipeline repo and copied in. This repo consumes data. It does not download or transform it.

The application entry point

A single flexdashboard document defines every page. It runs a Shiny runtime so maps and tables respond to user input. Concentrating the whole application in one file is unusual for a large site, and it is worth understanding the tradeoff. The benefit is that there is exactly one place to look, and the flow of the site reads in order from top to bottom. The cost is that the file is long and dense, so the practical way to work in it is to navigate by page and by the code chunk that builds each output, rather than reading it start to finish. Shared logic that would otherwise bloat the document is pulled out into scripts/functions.R, which is why that file is the second place to look when tracing how a map or table is built.

Folder by folder

The layout separates four concerns. The application itself and its shared logic sit at the top. Data lives under data/. The three render subsystems that produce standalone documents (scorecards, factsheets, and the national topic download) each have their own folder so their Quarto sources and assets stay self contained. Everything the browser loads directly, from stylesheets to images to finished PDF reports, sits under www/, which is the conventional home for web assets in a Shiny app. Reading the table below with those four groupings in mind makes the structure easier to remember.

The styling and accessibility layer

Two files carry the brand and the accessibility behavior for the whole site, and they are worth treating as first class parts of the architecture rather than afterthoughts. Accessibility is a core commitment of this project, not a finishing touch, so a good deal of care lives in these two files. The pattern to understand is that flexdashboard does not provide several things a fully accessible site needs, so the site adds them. A skip to content link, an explicit document language, and proper tab semantics with keyboard navigation are all injected by the code in cssloaders.html. When you change the navigation or add a page, it is worth confirming these behaviors still work, since they are layered on top of the framework rather than built into it.

FileWhat it provides
www/styles.cssCanonical EB Garamond load, design tokens, typography, table styling, focus rings, navbar and button colors, footer.
www/cssloaders.htmlFont preconnect, a skip to content link, a document language setting, the full WAI-ARIA tabs pattern with arrow key navigation, reduced motion support, and loading spinners.

How to update and deploy

Updates fall into two kinds, and it helps to know which kind you are making before you start. A data update changes the numbers and originates upstream in the pipeline, after which the refreshed datasets are copied into data/final/ here. A presentation update changes how the site looks or behaves and happens entirely within this repository. The environment is pinned by renv.lock, so a new maintainer should restore the locked packages first to match what the deployed site runs. The steps below cover the normal cycle.

  • Refresh data upstream. Run the pipeline in ADAPARCDataPipeline, then copy the five final Rds files into data/final/ here.
  • Edit the app in ADA_PARC.Rmd and shared logic in scripts/functions.R.
  • Adjust look and behavior in www/styles.css and www/cssloaders.html.
  • Deploy to shinyapps.io. Note that scorecards render at runtime, so a redeploy alone does not always refresh a committed scorecard HTML. Verify the fresh render.
